# V8 on Omi

How `v8hello.elf` is produced, and why each step exists. The short version: V8 is
built as a static library for **musl** with zig's clang standing in for Chrome's,
then linked into an embedder that Omi spawns like any other app.

Status: **the engine runs JavaScript on Omi.** On the ISO, `v8hello` prints

    [v8] js says 4999950000 and 2+2 is 4
    [v8] heap used 448 KB, version 16.0.0 (candidate)
    [v8] engine ran

and exits 0, with `[cxx] 12/12` still green beside it. See "Runtime blockers" for
the four things Omi had to answer to get there.

## 1. Fetch

    mkdir -p ~/v8 && cd ~/v8
    fetch v8            # depot_tools
    cd v8
    gclient sync --no-history --shallow -j4     # ~5.5 GB, mostly V8 + third_party

`--no-history` matters: V8's full history is tens of GB and none of it is needed
to build one commit.

## 2. Toolchain shim

V8's build drives `clang_base_path`, so the trick is to make that path a wrapper
around `zig cc`/`zig c++` targeting `x86_64-linux-musl`. zig's driver supplies
musl's libc, LLVM's libc++ (static) and libunwind, so a single static binary
comes out with no sysroot to assemble by hand.

`/home/meep/opt/clang-musl/bin/clang{++,}` is a bash script that must do four
things, each learned the hard way:

1. **Own the target.** gn and rustc both forward a glibc triple; zig refuses two
   `-target` flags. Strip any forwarded `-target`/`--target`.
2. **Validate flags.** zig's driver *rejects* options it does not know instead of
   forwarding them to clang. Probing every distinct `-f`/`-m` flag in
   `out/musl/*.ninja` against the driver found exactly four rejects:
   `-fno-lifetime-dse` and three `-fsanitize-ignore-for-ubsan-feature=*`. Drop
   those (none affect release codegen).
3. **Drop unimplemented linker options.** `--icf`, `-Wl,--no-*`, `-Wl,--lto-*`,
   and `-mllvm <arg>` all come from Chromium's config or Rust build scripts and
   are refused by zig's linker.
4. **Expose `sanitizer/` headers.** zig's resource dir has none, and
   `src/sandbox/testing.cc` includes `sanitizer/common_interface_defs.h`
   unconditionally. `-isystem` an overlay directory containing a single symlink
   to the system clang's `sanitizer/` subdir — *only* that subdir, so no other
   builtin header can be shadowed.

gn also derives two paths from the driver version and dies if they are missing:

    ~/opt/clang-musl/lib/clang/24/include               -> ~/opt/zig/lib/include (symlink)
    ~/opt/clang-musl/lib/clang/24/lib/x86_64-unknown-linux-gnu/libclang_rt.builtins.a

The builtins archive can be an empty one: it is only a dependency stamp for
archive targets, and zig supplies the real builtins at link time.

## 3. gn args (`~/v8/args.musl.gn`)

    is_debug = false
    is_component_build = false
    v8_monolithic = true
    v8_use_external_startup_data = false
    v8_enable_i18n_support = false        # ICU is 30 MB of data we do not need
    v8_enable_webassembly = false
    v8_enable_pointer_compression = false # wants a 4 GB reservation
    v8_enable_sandbox = false             # ditto
    cppgc_enable_caged_heap = false       # see below - the real blocker
    cppgc_enable_young_generation = false
    v8_enable_temporal_support = false    # only thing pulling Rust in
    v8_enable_ecma402_icu4x = false
    use_sysroot = false
    use_glib = false                      # else gn wants pkg-config for glib
    use_custom_libcxx = false             # zig supplies libc++
    clang_base_path = "/home/meep/opt/clang-musl"

Then:

    gn gen out/musl --args="$(grep -v '^#' ~/v8/args.musl.gn | tr '\n' ' ')"
    ninja -C out/musl v8_monolith -j3     # ~2 h on 4 cores, 94 MB archive

Use `-j3`, not `-j4`: four parallel heavy TUs on 18 GB gets OOM-killed
(`Killed` with no compiler diagnostic is what that looks like).

**Rust must stay out of the graph.** `v8_maybe_temporal` -> `temporal_capi` ->
Rust std, which is glibc-linked and cannot link against musl (`fstat64`,
`fstatat64` undefined). `v8_enable_temporal_support = false` removes it; verify
with `gn path out/musl //:v8_monolith //build/rust/std:std` printing
"No non-data paths found".

## 4. Runtime blockers on Omi

Each of these was fatal, in this order, and each is a fact about the kernel
rather than about V8:

- **cppgc caged heap** - Oilpan reserves a 4 GB heap cage on *every* 64-bit
  build, even with the sandbox off, and dies with
  `Fatal process out of memory: Oilpan: CagedHeap reservation`. Omi gives a
  process a 222 MB mmap window inside a 4 GB address space, so this can never be
  satisfied. It is a `declare_args` variable, so turn it off and rebuild; the
  young generation asserts on the cage and comes off with it.
- **`madvise` (28)** - V8's GC returns pages with `MADV_DONTNEED`/`MADV_FREE` and
  CHECKs the result, so `-ENOSYS` kills the process. `linux_madvise` releases the
  span through `vm_release_range` (the next touch faults in a zero page) and
  succeeds for the pure hints.
- **`munmap` (11)** - `sys_vm_free` used to require the range to sit inside a
  single area and return `-EINVAL` otherwise, which tripped
  `Check failed: 0 == munmap(address, size)` at shutdown. It now takes the
  intersection with every overlapping area, trims front or back, and releases a
  whole area when the range covers it. A hole in the middle keeps its record and
  reads as zeroes afterwards - one record per area cannot express a split.
- **A futex word is 32 bits, and this kernel compared eight.** musl's `LOCK()`
  packs a sign bit and a congestion count into an `int` and passes the expected
  value sign-extended, so a contended lock waits with `0xFFFFFFFF80000000`.
  `sys_futex` read the word as a `long` and compared all eight bytes: the upper
  half of the word was zero, the expected upper half was all ones, so the compare
  never matched and every waiter got `-EAGAIN` and retried for ever. A thread
  parked on a semaphore handoff never progressed - `userland/handoff.c` now
  proves 2000 rounds of `sem_post`/`sem_wait` finish. Fixed by comparing the low
  32 bits, which is what Linux's futex contract actually specifies.
- **`~DefaultPlatform` waits on worker threads.** `platform` is a stack object,
  so returning from `main` destroys it, and that destructor terminates the
  worker runners and waits for them; on Omi that wait never returns. The symptom
  is exactly "exit() hangs": no atexit handler runs (main never gets that far),
  and the process is never reaped. The embedder leaks the platform on purpose,
  as V8's own samples do. Which thread is supposed to post that semaphore is
  still open - see `docs/linux-abi.md` and the roadmap.

## 5. Link and run

    zig c++ -target x86_64-linux-musl -std=c++20 -static -O2 -no-pie \
      -Wl,--strip-all -I ~/v8/v8/include \
      -o v8hello.elf v8hello.cpp ~/v8/v8/out/musl/obj/libv8_monolith.a -lpthread

`-no-pie` is required: Omi loads ET_EXEC at a fixed base. 24.5 MB stripped;
Omi's loader mapped it without trouble.
